# Stock scanner acquisition fixture

`scanner_fixture.py` executes stock scanner routines using the existing
`Fixture`/`BootTrace` model. It is an independent offline command: it does not
build or edit the hybrid app, access USB, or use a hardware tunnel.

It demonstrates a small call sequence suitable for a future hybrid scanner
adapter: initialize profiles, power on, build exposure/AFE/DMA parameters,
perform finite stationary acquisition, and power off. It also records the RAM
and flash ranges used by that sequence. The stock image is hash-pinned by the
existing input loader.

## Run

From the public firmware repository, supply a saved 1,024-byte EEPROM image.
Use the existing `mg2550s-emu` Docker image, or build it with
`docker build -t mg2550s-emu emu`. Native macOS Unicorn has crashed on this CPU
model; Docker is the tested execution environment.

```sh
mkdir -p emu/output/scanner
docker run --rm --network none \
  -v "$PWD:/project:ro" \
  -v "$PWD/emu/output/scanner:/out:rw" \
  -v "$PWD/emu/inputs/eeprom.bin:/eeprom.bin:ro" \
  mg2550s-emu emu/stockapp/scanner_fixture.py \
  --eeprom /eeprom.bin --output /out/scanner.json
```

On native Linux with `emu/requirements.txt` installed:

```sh
python3 emu/stockapp/scanner_fixture.py \
  --eeprom emu/inputs/eeprom.bin --output emu/output/scanner/scanner.json
```

Verification always runs and a failed expectation exits nonzero. The output
must be a `.json` path distinct from the EEPROM input. Reports include detailed
MMIO writes and service calls; they contain no captured document pixels.
Different EEPROM inputs may change boot state and reference expectations.

## Checks and reference results

See [the compact checked result](../evidence/stockapp/scanner/finite_summary.json).

| Scenario | Checked result |
|---|---|
| P7 diagnostic, one line | Returns after two IRQ18 and five IRQ19 callbacks. |
| P0, one/two/four lines | N requests, N+4 IRQ19 callbacks, expected two-channel windows. |
| P0/P6, three components, four lines | Four mask-7 requests; larger windows and changed initial pointers/skips. |
| Repeated P0 capture, no state reset | Same timing; previously applied AFE parameters are reused. |
| Rebuild AFE parameters, gain 5 | Nine serial transfers; both segment gain registers receive 5. |
| Withhold IRQ18, IRQ19, or AFE completion | Corresponding native wait remains blocked; no fake completion. |
| Omit scanner power-on | Timing returns but no operating AFE setup is performed. |
| Five synthetic gain statistics | Stock P0 type-0 computation yields 13, 13, 10, 4, 3. |

The checks also verify finite cleanup, power-off, and unchanged stock image and
pixel-buffer canaries. A capture return leaves an incidental register address
in r0; it is not a boolean result API.

## Model boundaries

- Uses readiness level 4 and type-0 AFE response `0x40`, with a full stock boot
  RAM snapshot. This does **not** validate the hybrid's sparse snapshot.
- Calls stock Thumb routines and handlers directly with IRQ/FIQ masked. The
  small event adapter implements set/clear/wait; waits resume only after real
  stock handlers post their event. Delay calls return immediately.
- IRQ18, IRQ19, and serial interrupt delivery are explicit test inputs. They
  are not generated by physical line timing. There is no scheduler during
  these calls, and elapsed time/settling requirements are not validated.
- No pixel DMA, optics, motor movement, colour order, or DMA completion fence
  is modeled. The image buffer deliberately stays unchanged even in returning
  captures. These tests establish configuration/control flow, not an image.
- The tested finite input adapts the diagnostic request shape to optical
  profiles and line/component counts. It is not a recovered normal host scan
  job. P7 itself is diagnostic, not an optical image baseline.
- Configuration and buffer addresses are fixture scratch. They must not be
  copied into the hybrid's allocation map.

`ram_pages_touched_4k` can be consumed by `ram_snapshot.py --reports` alongside
the existing reports. `flash_coverage` records code and data ranges for this
subset. Reassess coverage before adding calibration, moving scans, or colour.
Stock boot state, optical routines, and calibration remain explicit temporary
dependencies to replace with documented C implementations.
